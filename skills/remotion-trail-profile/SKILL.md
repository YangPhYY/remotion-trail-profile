# 轨迹 + 海拔剖面同步动画（Remotion + 调参台）

把一条 GPS 轨迹变成视频：轨迹按里程从左到右生长，剖面游标同步扫过，
游标处海拔 = 地图头部位置的海拔（**严格一一对应**，不靠肉眼对）。

本机参考实现：`D:\办公资料\workbuddy\remotion` 的 `TrailProfile` 合成
（`src/trail-geo.mjs` / `src/trail-scene.mjs` / `src/TrailProfile.tsx` / `trail-studio.html`）。

## 0. 三种产品形态，先问清楚

| 形态 | 观感 | 参数 |
|---|---|---|
| **平面全景**（推荐默认） | 整条轨迹一屏静止，轨迹生长 + 剖面条从暗到亮、游标从左到右扫 | 相机与帧无关；剖面「整条显示」 |
| 跟随滑动 | 相机锁住轨迹头部，轨迹从右向左滑过画面 | 相机锁头部 + 前瞻距离；剖面「跟随窗口」 |
| **卫星截图叠加** | 用户给一张卫星截图，轨迹直接长在真实影像的道路上；无剖面 | 见 §12（另一套合成 `SatelliteTrack`） |

「去掉地图滑动和镜头跟随」== 平面全景 + 相机与帧无关。别只把参数默认值改掉，
要**把跟随分支从场景模型里真的去掉**，否则两套相机模型会长期互相污染。


## 1. 架构：三方共用，只有一个真相源

```
src/trail-geo.mjs      几何/相机（纯 ESM，无依赖）—— Remotion / 取瓦片脚本 / 调参台三方共用
src/trail-scene.mjs    buildTrailScene(geo, D, props, frame, cfg) → 纯数据「场景对象」
src/TrailProfile.tsx   只做「把场景对象塞进 SVG/DOM 属性」
trail-studio.html      调参台：调**同一个** buildTrailScene，只是外面套 CSS 缩放
```

- **唯一自变量** `frame → progress → distM`。地图头部、剖面游标、海拔读数全由同一个 `distM` 推出。
- 数据按**等里程重采样**（stepM 固定，如 10 m）→ 下标 `i ↔ i×stepM`，按里程取点退化成 O(1) 线性插值，
  对齐由**数据结构**保证，而不是靠调用方小心。
- 参数按**分组深合并 + 逐字段 `??` 兜底**：CLI `--props` 与 `defaultProps` 是浅合并，
  只传 `{"海拔剖面":{"高度":200}}` 会把整组替换掉。
- 几何/参数的唯一真相源是**文件**（如 `*-defaults.json`），组件与调参台都读它。

## 2. 相机铁律

**全景适配（`fitCamera`）必须两个方向取较小者**：

```js
k = Math.min((screenW * ratio) / bboxW, (screenH * ratio) / bboxH);
gx = posX * (screenW - bboxW*k) - bbox.minX * k;   // posX: 0=贴左 1=贴右
```

- 只按宽度算 → 扁轨迹竖向顶出画面被切掉；只按高度算 → 横向一片空白。
- 所以「轨迹占比」是**两条边各自最多占多少**，实际横向占比常小于设定值，这是几何决定、不是 bug。
  想让轨迹更宽只能把剖面调矮（地图区变高）或换画幅。
- 跟随相机：`k = screenW * mpu / camWidthM`（`mpu = 40075016.7 * cos(latRef)`）。
  两轴必须用同一个 k（墨卡托等角），否则轨迹被拉伸。

**`toScreen` 是闭包方法 —— 平移只能重建相机对象**：

```js
// ✗ 错：展开对象只改字段，toScreen 仍按旧中心投影
cam = { ...cam, cx: cam.cx - dx/k };
// ✓ 对
cam = panCameraPx(geo, cam, dx, dy);   // 内部重新 makeCamera
```
踩过的后果：轨迹组（吃 `gx/gy/scale`）平移了、瓦片与头部（吃 `toScreen`）没动，底图与轨迹直接错开。

**局部绘制按墨卡托弧长归一**，不是里程：纬度差会让两者差 ~0.04%（31 km 上 ≈14 px）。
用 `mercLengthFractions()` + `pathLength=1` + `strokeDasharray="frac 1"`。

## 3. 剖面「整条显示」：曲线静止、游标移动

令 `ppm = plotW / totalM`、`cursorX = plotLeft + distM*ppm`，再把 `windowM = totalM` 传给
`profileX(distM, d, cursorX, windowM, axisW) = cursorX + (d − distM)*ppm`：

```
→ plotLeft + distM*ppm + (d − distM)*ppm = plotLeft + d*ppm
```

曲线 x **与帧无关**（一屏铺满），游标随里程从左到右扫，「已走」用 `clipPath` 以 `cursorX` 为界。
比「跟随窗口」实现更简单，观感更符合「一页看完」。

**游标读数必须横向钳制**（`text-anchor="middle"` 时中心 = `cursorX`）：
里程 0 时它会压住左侧「上限 m」刻度标签（实测「800 m」与「640 m」直接叠成一串），
100% 时又顶到画布右缘。按 `readoutHalfW()` 估半宽，
`x = clamp(cursorX, 轴标签右缘+22+半宽, min(plotRight, width−14)−半宽)`。
只钳横向，纵向仍由「读数上移」控制；**下限留 22 px 而不是 10 px**，10 px 看着还是粘在一起。

## 4. 自由添加途经点

参数里存 **JSON 字符串**（如 `轨迹.自定义途经点`），结构：

```json
[{"名称":"南天门","里程km":2.1},
 {"名称":"营地","经纬度":[113.05,34.48],"颜色":"#FF7043"}]
```

- **两种定位**：`里程km`（首选 —— 与剖面游标同一套里程，剖面上看到哪就加在哪）或
  `经纬度`（**吸附到最近的轨迹样本点**，用户从地图取点很难正好落在线上）。
- 坐标一律由 `sampleAt(geo, distM)` **反查**，不直接用用户给的坐标 → 标签必然落在轨迹上。
- 解析要**带缓存**（调参台每帧都会问一次，而经纬度吸附是 O(样本数)）。
- 坏数据（无名称 / 无定位 / JSON 打错字）必须**跳过而不是抛异常** —— 不能把整个合成打崩。
- 调参台给专用列表编辑器 + 「＋ 加在当前里程 xx.xx km」按钮（拖播放条就地打点）。
  JSON 非法时**保留原文 + 只读 textarea 修正**，绝不抹掉用户数据。

### 4.1 样式体系：标记形状必须算成「纯数据图元」

需求形态通常是「让我自己自由调整途经点的位置和样式（字号/颜色/形状）」。**别在两个渲染方各写一遍
形状推导**（React 写一套 SVG、调参台写一套字符串）—— 那必然分叉成「调参台好看、出片不一样」。

正确做法：形状几何只在场景模型里算**一次**，产出与渲染技术无关的图元数组。

```js
// trail-scene.mjs —— 唯一形状真相源
export const WP_SHAPES    = ["圆点","圆环","菱形","方块","三角","图钉","十字","无"];
export const WP_LABEL_POS = ["上","下","左","右","无"];
export function markShapes(shape, s, color) {
  // 返回 { ext, shapes }；shapes 元素是本地坐标（原点 = 标记中心）的纯数据：
  //   {t:"circle", cx,cy,r, fill?, stroke?, sw?, so?}
  //   {t:"path",   d,     fill?, stroke?, sw?}
  //   {t:"line",   x1,y1,x2,y2, stroke?, sw?}
}
```

- `ext` = 标记在四个方向的**外沿半径**，供标签让位：`gap = ext + labelGap`
  → 换大形状标签自动让开、不压字。下方向还要额外让开基线：`dy = gap + fontSize*0.78`。
- `sw = (f) => Math.max(1, s * f)`：小尺寸下描边也要可见。
- **两个渲染方各只写一个「按 `t` 建元素」的小 switch**（React 建 `<circle>/<path>/<line>`；
  调参台拼字符串），外面套 `transform="translate(x,y)"`，**都不做形状推导**。
- 枚举 `WP_SHAPES`/`WP_LABEL_POS` 从场景模型 **export**，参数表（select 选项）与校验 schema
  **直接 import 复用**，绝不写第二份 —— 否则加一个形状要改三处、漏一处就静默失效。
- **新增形状只改 `markShapes` 一处**，两个渲染方零改动。

**样式字段的三态语义**（决定「跟随默认」能不能用）：

- `null` / 缺省 = **跟随全局默认**（之后改全局会带动它）
- 有值 = **单点覆盖**
- 调参台的「↺ 跟随默认」必须用 **`delete w[k]`**，**不能写回当前全局值** ——
  写回等于固化成覆盖，以后再改全局它就不跟了。
- 全局默认放同一组参数里（形状/大小/标签位置/标签偏移/透明度），逐点用 `w.xxx ?? wpXxx` 兜底。

### 4.2 画布直接拖动/点击改位（换算链必须完整）

```
屏幕坐标 → 除舞台 CSS 缩放 → 反解相机 (gx,gy,k) 回墨卡托
        → nearestDistOnTrack() 取最近轨迹点里程 → sampleAt() 反查轨迹坐标
```

- `nearestDistOnTrack()` 要从场景模型 **export** 出来复用，别在调参台重写一遍最近点搜索。
- **回写保留原定位方式**：原本按经纬度定位的点，拖动后仍写回**吸附后的真实经纬度**
  （往返稳定），不要悄悄变成里程点，否则用户下次打开会看到定位方式被改掉。
- 「定位到该点」要与播放头一致 → 用**缓动函数的二分反解**把里程映射回帧号（生长是缓动的，
  别直接用 `distM/总长 × 帧数`）。
- 拖动往返误差要有断言（实测 < 1 m）。
- **★ `wpIndex` 必须是原始数组下标，不是输出序号**：解析会跳过「隐藏 / 无定位」条目，
  用输出序号做命中检测 → **画布上拖 A 点会改到 B 点**。解析时显式记 `wpIndex: idx` 并加断言钉住。

### 4.3 两个交互坑

- **`setPointerCapture` 在合成事件下抛 `NotFoundError`**：CDP / 自动化造的 `PointerEvent`
  没有真实 pointerId → 必须 `try { hit.setPointerCapture(e.pointerId); } catch {}`，
  否则自动化验证时拖动逻辑直接崩，且崩在中间不容易看出是它。
- **画布交互要单独一层 `#hit`**（`cursor: crosshair/grab`），与 SVG 渲染层分开；
  命中半径取 `Math.max(16, size*2.6)`；空白单击 = 在该位置加点。
- **断言「两种形状不同」不能比图元数量**：圆点与图钉恰好都是 2 个图元，`length !== length` 会误报。
  比 `JSON.stringify(A.shapes) !== JSON.stringify(B.shapes)`。
- 新增点写入 JSON 时要**跳过空值字段**（`颜色:""` 之类会变成噪声，还会把「跟随默认」误判成覆盖）。

## 5. 调参台（trail-studio.html + 本地服务）

- 参数面板**由参数表 `PARAM_GROUPS` 生成**，不手写几十个控件；
  滑块 min/max 必须与 zod schema 一致，否则「页面能拉到 4000、粘进 Studio 被拒」。
- 预览调**同一个** `buildTrailScene`，杜绝「调参台好看、出片偏了」。
- 保存走本地服务 `POST /api/save-props`，落盘前 `clampPropsToSpec()` 裁剪。
- **性能**：长 path（`d` 上千点、几十 KB）单独成一层，只在「慢变量」变化时重建 DOM，
  每帧只改 `stroke-dasharray`；`<defs>` 的缓存 key **不能包含每帧都变的量**（如游标 x）。
- 暴露 `window.__trail`（PROPS / frame / setFrame / 业务查询函数）——
  ES 模块内的变量外部读不到，否则自动化断言「点了按钮到底写进了什么」就没法客观核对。
- **常用开关要额外放一个「底栏快捷入口」**：只塞在折叠组里、标签还叫「显示」时，
  用户找不到（「增加海拔图开关」这类要求，本质是找不到而不是没有）。
  做法：底栏 `<input type=checkbox id="chk-profile">` + 参数表里同键的 item 标 `label:"显示海拔图"`，
  两个入口写**同一个键**（不复制状态），再把这个键 `controls.push({primary:cb,set})` 进同步数组，
  由 `syncControls()` 双向回填 —— 复制成两份状态必然出现「一处关了另一处还亮着」。
  现在有两组这样的入口：`chk-profile`（海拔剖面 · 显示）/ `chk-track`（轨迹 · 显示轨迹）。
  「显示轨迹」是**地图叠加层的总开关**：线、头部点、起终点、标注、途经点一起关
  （只关线条会留下悬空标签）；底图不归它管，仍由「地图 · 显示底图」单独控制。
  所以「只出海拔图」= 关轨迹 + 关底图 + 开剖面，三个开关互不耦合。
  隐藏时调参台要同时把画布交互层置 `off`（`#hit`），否则会拖到看不见的点。

### 两个必踩的坑

1. **「内容没变就跳过重建」会把首屏也跳过**：初始内存值与文件里的值相同 →
   首屏空白。加 `el.dataset.ready` 标记，只对已渲染过的做无变化跳过。
2. **服务是长驻进程**：改了参数表必须**重启服务**，否则页面能看到新键、
   保存时却按内存里的旧表重建对象，把新键无声抹掉。
   防御：`clampPropsToSpec` 保留「参数表之外的键 / 未知分组」。

## 6. 客观核对（不要靠肉眼）

`scripts/check-trail-align.mjs` 的断言清单（每帧抽样，缺一条都会出「看着对其实错」的片子）。
> 本仓库未附带这个脚本；下面是它该断言的内容，按此自行实现即可（30 行左右的纯函数校验）。

1. 读数同源：游标数字 == 右上 HUD == 同里程平滑海拔
2. 游标落在曲线上（折线在 `cursorX` 处插值 == `cursor.dotY`）
3. 相机往返：头部屏幕坐标反投影 == `sampleAt(geo, distM)`
4. 整条模式：曲线首尾 == 绘图区左右边界，且**逐字符与帧无关**；游标 x 与里程成正比
5. 峰位交叉验证：**密集扫描**（步长 2 帧）且**只比里程、不比帧号**（生长缓动可非线性）
6. 瓦片齐备（仅开启底图时）
7. 整条轨迹完整在画面内（检查 bbox **四个角**）
8. 头部屏幕坐标与轨迹组 `(gx,gy,k)` 出自同一相机
9. 底图瓦片与轨迹同源（仅开启底图时）
10. 相机逐帧恒定 —— 「去掉滑动/跟随」的可验证形式
11. 自定义途经点落位（里程 / 经纬度两种都要验）
12. 途经点样式体系：参数表枚举与场景模型**同源**；每种形状的图元数与标签外沿 `ext`；
    4 个标签方向的间距与 `text-anchor`；`"无"` 不产标签；逐点覆盖 vs 全局默认（改全局要带动未覆盖点）；
    非法值回落；隐藏/无定位被跳过；`wpIndex` 保留原始下标；**拖动换算链往返误差 < 1 m**

**★ 断言里的取样里程必须按 `GEO.totalM` 取比例，绝不写死 km**：
写死 `[1, 8.3, 15.7, 22.86, 29.9]` 的上一条 31 km 轨迹，换到 2.9 km 的新轨迹后
取样点全被钳到终点 → 「往返误差 < 1 m」报 **26980 m 假红**，而「两点的几何不同」
「标签间距」这类断言又退化成同一位置、静默变成空断言（照样打勾）。写成 `KMN(frac)` 一行就治本。

**★ `nearestDistOnTrack` 必须是「逐线段投影 + 里程插值」**：
只比「离哪个样本顶点最近」时，10 m 步长下最大偏 5 m（实测新轨迹上 4.478 m），
既让拖动吸附不跟手，也让上面的往返断言假红。逐线段投影后误差 < 0.01 m。

调参台交互用 CDP 实拍核对（可选工具，本仓库未附带）：
`node scripts/cdp-shot.mjs --url=... --wait="条件" --seq='[{"expr":"...","out":"out/x.png"}]'`。
顺带把「点击加点确实落在指定 km」「拖动 8 km→20 km」「展开明细行」「改样式确实写进 JSON 且渲染生效」
「跟随默认确实清掉了覆盖键」都各断言一次 —— 这五件事肉眼在截图上看不出来。

### 形状系统必须渲一版「对照图」

新增/修改形状后，用**真实出片路径**（Remotion 渲染，不是调参台预览）渲一张
「所有形状并排 + 各自带标签」的静帧主观检查 —— 要确认的是标签**让位**正确（没压到标记上）、
小尺寸下描边可见、`"无"` 真的什么都不画。这类问题在调参台小预览里看不出来。

## 7. 出片与国内环境

### ★ 先砍滤镜，再谈并发（最重要的性能铁律）
本机走 `chrome-headless-shell + SwiftShader`，**纯 CPU 光栅化**。SVG `feGaussianBlur` / CSS `filter`
的开销 ≈ **滤镜区域面积 × 核宽**，跟「静态还是逐帧重建」几乎无关 —— 静态滤镜一样能吃掉大半渲染时间。

实测（同上 12 帧，只差「显示光晕」一个开关）：

| 配置 | 12 帧耗时 | 每帧 |
|---|---|---|
| 光晕开（`stdDeviation`≈24 px，滤镜区 = 整条路径包围盒 ≈1500×700 px） | **107.4 s** | 7.3 s |
| 光晕关 | **39.4 s** | 1.6 s |

光晕占 **2/3** 总耗时，而深色底上白光晕**肉眼几乎看不出差别**（被粗线本身盖住）。
所以：**`轨迹.显示光晕` 已在 `src/trail-profile-defaults.json` 里定为 `false`**（2026-10-30 用户拍板：
以后默认关闭），出片**不必再传 `--props` 去关它**，也别把它改回 true。用户明确说「要光晕」时才临时开，
且先想办法缩小滤镜区域（只对可见段做滤镜 / 缩小 `stdDeviation` —— 开销按核宽近似平方下降），别指望提高并发。
关掉后 1080p 稳定 **1 帧/秒**，46.5 s 成片 1395 帧 × 并发 5 ≈ **29 分钟**。

排查渲染慢的**次序**：① 有没有大范围 SVG 滤镜/CSS filter → ② 有没有残留进程抢 CPU → ③ 才轮到元素数/路径点数。

- 渲染加 `--browser-executable "<chrome-headless-shell 路径>"`（国内下不了官方 Chrome），
  并发 1~5、`--timeout=90000~120000` 配 `--gl=swangle`（stderr 里 WMIC 黑名单告警非致命）。
- **动手前先清残留**：被中断的 `remotion render` 不会自己退，孤儿 `chrome-headless-shell` 会持续空转
  （实测某孤儿累计 2609 s CPU，而正在渲染的浏览器只有 2~10 s → 12 分钟一帧未出）。
  判据 `Get-Process chrome-headless-shell,node | Sort CPU -Desc`，先 `taskkill /F /IM chrome-headless-shell.exe`。
- **★ 但 `taskkill` 浏览器 ≠ 结束渲染任务**：父进程会**重新拉起浏览器跑完并覆盖同名输出**。
  实测：把一次带光晕的渲染判成卡死、重跑了一版关光晕的并已交付验证，20 多分钟后那个「已中断」的任务复活，
  跑满帧数把 `out/*.mp4` 覆盖了。要真正放弃一次渲染必须结束**后台任务本身**（或杀掉对应 `node.exe`）；
  **最终出片必须等所有旧渲染任务确认结束后再做，写完立刻核对文件 mtime/字节数**——
  同一命令渲两遍字节数不同，正好用来识别输出被顶替。
- **进度不要接管道**：`remotion render ... | tail -30` 会缓冲掉进度，中途完全不可见。
  改重定向到日志再读：`tail -c 3000 out/render.log | tr "\r" "\n" | grep Rendered`。
  且 Remotion 自报的 "time remaining" 在启动阶段严重高估（报 2h21m，实际 19 min），
  要算 ETA 就自己采样两次帧数求斜率。
- **核对成片规格用 Remotion 自带 ffmpeg**（本机常没装 ffprobe，`ffprobe-static` 也不在）：
  `node_modules/@remotion/compositor-win32-x64-msvc/ffmpeg.exe -i out/x.mp4` 看 `DAR 16:9`/时长/编码；
  抽帧核对同样用它：`-ss <秒> -frames:v 1 -y out/x.png`。**交付前务必抽 3 帧（开头/中段/结尾）实际看图** ——
  本次就是这样发现了「游标在最左端时读数与纵轴标签相撞」「在最右端时读数贴边」两处首尾瑕疵，
  这两处光看中间帧永远发现不了。
- `public/` 里若有几百 MB 其它合成的素材，用 `--public-dir=.public-trail` 只放本合成需要的文件，
  否则每次多花几十秒拷贝（实测 381 MB / 43 s）；注意 Remotion **不跟随 junction**，要真拷贝。
- **批量 `rm -rf` 会被安全守卫拦下**（单轮 >50 个文件需确认），拦下时整条命令 `EXIT=1` 立即失败 ——
  若把清理和渲染写在同一行，渲染根本不会启动。清理要分批或先确认文件数。
- 高德瓦片：`webst0{1-4}.is.autonavi.com/appmaptile?...&style=6`（**JPEG 不是 PNG**，
  用 PNG 魔数校验会把每张都判成非法响应）。离线预取后渲染零网络请求。
  取瓦片范围**直接问场景模型要**（`buildTrailScene(...).map.tiles`），别用包围盒估算。
  底图若默认关闭，则出片**不需要**任何瓦片，`--public-dir` 只放必要的即可。

## 7.5 路型：把「线」画成「路面带」

轨迹不再是一条线，而是按里程切成若干段，每段有**宽度 + 底色 + 材质 + 路型名**。
开关在顶部工具栏「路型」，与参数「路型 · 显示路型」是同一个键，双向回填。

| 路型 | 宽度 | 底色 | 材质（真正让人一眼认出的特征） |
|---|---|---|---|
| 公路 | 1.35× | 沥青 `#3A4048` | 两侧白边线 + 中央黄虚线 —— **白边线才是识别点**，沥青灰在缩略图上会跟台阶混 |
| 机耕路 | 1.15× | 土黄 `#A87E52` | 碎石颗粒 + 两条人字胎印（分居两侧，间距 0.48 带宽） |
| 土路 | 1.0× | 浅土 `#C7A87D` | 深浅斑驳 + 亮沙点 + 路肩毛边虚线 |
| 步道台阶 | 0.9× | 岩灰 `#7C8897` | 横向梯级：每条 1.5px 亮踏面 + 后移 1.8px 的暗立面（假 3D） |
| 陡坡山路 | 0.75× | 砖红 `#C2410C` | 45° 深红斜纹，间距最密 |
| 攀爬 | 0.62× | 赭褐岩 `#5A4A3B` | 岩点（浅灰/琥珀交替）+ 层理裂纹。**不要灰底 + 中线**，那看着像公路（踩过的坑） |

宽度即信息：能走车的宽、要手脚并用的窄，不看图案也能排出序。

**参数（路型组共 10 项）**

| 键 | 默认 | 说明 |
|---|---|---|
| `显示路型` | true | 关掉 = 回到原来那条单色细线；**分段为空时开关没有任何视觉变化**，这是新手最容易误判成「开关坏了」的地方 |
| `路型分段` | `[]` | JSON 数组，起止写**途经点名**或**里程 km**，末端可写 `"终点"` |
| `路型带宽倍数` | 2 | ×线宽。实测 2×（12px）能认出形状但数不清石子；3~4× 才看得清碎石 |
| `路型色相强度` | 0.85 | 拉到 0 → 全部退回主色，只靠形状与材质区分 |
| `纹理密度` | 1 | 材质间距倍数 |
| `段首徽标` | true | 路型名，画在**段中点**（段首往往正压着途经点标签） |
| `徽标位置` | 自动 | 自动 = 沿法向左右交替；上/下/左/右是**屏幕绝对方向**，选左右会自动把 anchor 切成 start/end，否则文字压线 |
| `徽标偏移` | 0 | −120~200 px，负值会贴到线上 |
| `徽标字号` / `徽标颜色` | 17 / 白 | 带黑色描边，保证任意底色可读 |

**坡度角放在海拔剖面里，不在轨迹上画箭头**：
`剖面坡度标注` + `坡度标注下限`(默认 8°) / `坡度标注字号` / `坡度标注上移` / `坡度标注颜色`；
游标侧另有 `坡度读数` + 字号 / 上移 / 颜色。
标注取**段内最陡 200 m 窗口**，不是整段平均 —— 2.9 km 环线累计爬升 119 m，整段平均只有 4°，标出来全是「↗3°」等于没标；
游标读数才用整段平均，避免数字逐帧乱跳。

**四条实现要点（改代码前必读）**

1. **「已走 / 未走」不能靠覆盖**。老实现是白色实线盖在草图上，一加纹理就被整段盖掉。现在是同一段画两遍：
   压暗底（未走）+ 提亮底（已走，`pathLength=1` + `dasharray` 裁剪），材质单独一层，按 `decorAlpha` 在「走到」时提亮。
2. **材质图元必须用屏幕坐标**。用墨卡托坐标输出时尺寸只有 `8.3e-8`，在 `scale(2.2e7)` 的组里直接触发浮点精度下限，
   图元**静默消失**（不报错、什么都不画，最难查）。`decorOf()` 因此吐屏幕 px，渲染端要放在**不缩放**的层里。
3. **台阶横杠要逐点算法向**。`dash` 画不出垂直横杠，必须按弧长采样 → 算切向 → 取法向，才能保证拐弯处不歪。
4. **调参台按 key 缓存 DOM 时，切走的分支必须重置缓存**。路型层用 `roadRefs.bandKey` 判「要不要重建」，
   切回单线时没重置 → 再打开路型时判定「key 没变」→ 画面停在单线（症状：关掉再打开，路型回不来）。

**换轨迹必清 `路型分段`**：分段按名字或里程写死，换轨后名字一律匹配不到 → 整层静默失效
（`road=null`，悄悄退回单色线，不报错）。设计文档见 `docs/路型样式-需求与提示词.md`。

## 8. 推荐默认设定（起点，不是硬性规定）

目标形态：「一条轨迹 → 一眼能看懂 → 直接进剪映叠」，不是技术演示。
下表是长期使用后沉淀的推荐值；要换风格就整表覆盖，不必逐项解释。

| 设定项 | 取值 | 为什么 |
|---|---|---|
| `地图.透明背景` | **true** | 成品要叠在剪映真实画面上，alpha=0 是刚需 |
| `轨迹.显示光晕` | **false**（已写进 defaults，不必每次传 props） | 深底上肉眼几乎看不出，却吃掉 2/3 渲染时间 |
| `路型.路型带宽倍数` | 2（=12px） | 细线审美与可读性的折中；3~4× 才能看清碎石，但画面会变"粗管子" |
| `路型.段首徽标` | true | 形状能自证时，名字只是把含义再确认一次，不铺满全程 |
| `海拔剖面.剖面模式` | 整条显示 | 一屏看完，不要跟随窗口 |
| 相机 | 平面全景（无跟随/滑动） | 地图不滑，只有轨迹长 + 游标扫 |
| `动画节奏.时长秒` | 45 | 40~46 s 之间可接受 |
| `文字标题.主标题` | 「<你的署名>」+ 轨迹名 | ⚠ 换轨迹后**必须**改，否则还挂着上一条的名字 |
| 首次交付形态 | **调参台**（不渲染） | 见 §8.5：先调后渲，否则白渲一遍 |

**交付标准（缺一条不算完成）**
1. 抽**首 / 中 / 尾 3 帧**实看 —— 中间帧永远发现不了首尾瑕疵（游标贴边、读数撞轴）。
2. 透明片必须验 alpha：四角 `0,0,0,0`，且非透明像素 > 1%（否则是空片）。
3. 标题、里程、爬升与这条 KML 一致。

## 8.5 ★ 交付边界：默认只到调参台，不自动渲染出片

用户说「帮我把这条轨迹生成轨迹动画」时，**默认交付物 = 调参台里能调能看的活状态，不是 mp4。**
一版 45 s 的片子是 5~15 分钟软件渲染，而路线分段、时长、标题九成还要改 —— 先出片基本等于白渲。

**规则（按顺序判断）**
1. 收到 KML → 解析数据 → **清掉上一条轨迹遗留的引用** → 打开调参台 → **停在这里**。
   - 「自定义途经点」里按名字/里程写死的点、「路型分段」里按名字引用的区间，换轨迹后**一律匹配不到**。
     前者会画到山外，后者会让路型整层静默失效（回到单色线）。所以换轨必清。
   - 旧数据先备份成 `*.bak-<旧轨迹名>`，别覆盖掉。
2. 收尾时必须**明确问一次**「要不要现在直接渲染导出？」（有选项组件就用选项，没有就问一句话）。
3. **例外**：用户话里已经带「渲染 / 出片 / 导出 / 视频 / mp4 / 发我」这类明确动词 → 直接渲染，不必再问。
4. 真要渲染时，先按 §8 那张表过一遍参数（透明背景、标题改成本条轨迹名）。光晕已在默认值里关掉
   （`轨迹.显示光晕 = false`），**不要手动打开** —— 它不是审美选项，是渲染时间的三分之二。

**为什么写死这条**：换轨迹最常见的返工不是渲染失败，而是「渲完发现标题还是上一条」「路型分段全空」
「途经点标记跑到山外」—— 这三样在调参台里 30 秒就能发现，渲染却要等十几分钟。

## 9. 标准作业顺序（SOP，一条 KML 从零到片）

```bash
# ① 解析 KML → 等里程重采样（唯一真相源，输出 src/trail-profile-data.json）
node scripts/build-trail-profile.mjs "<kml 路径>" --step=10
# 输出确认：点数 / 里程 / 海拔区间 / 爬升 / 坐标系判定（WGS-84 自动转 GCJ-02）
# 没有高德 key、或坐标是虚构示例时，加 --no-verify 跳过坐标系校验

# ② 调参台微调（只需 Node，不用 npm install）
node scripts/trail-studio-server.mjs        # http://localhost:5232/trail-studio.html
# 改完点「保存到文件」，写回 src/trail-profile-defaults.json

# ③ 生成完整 props（⚠ CLI --props 是浅合并，**必须传完整 defaults**，只传子组会把整组替换掉）
node -e "const fs=require('fs');const d=JSON.parse(fs.readFileSync('src/trail-profile-defaults.json','utf8'));
d.文字标题.主标题='<轨迹名>';d.轨迹.显示光晕=false;d.地图.透明背景=true;
fs.writeFileSync('out/trail-props-alpha.json',JSON.stringify(d,null,2));"

# ④ 抽首/中/尾 3 帧实看（必做，别跳）
for f in 60 700 1340; do ./node_modules/.bin/remotion still src/index.tsx TrailProfile \
  "out/check-$f.png" --frame=$f --props=out/trail-props-alpha.json; done

# ⑤ 出片（透明 ProRes 4444，剪映/PR 通用，体积大）
npm run render-trail-alpha
```

判定「轨迹与剖面是否严格同步」不要靠肉眼，走 §6 的客观核对。

## 10. 环境准备与已知坑（核实日期 2026-10；环境会变，动手前先 `ls` 验一遍）

- **浏览器**：Remotion 需要 Chromium。自带 `chrome-headless-shell` 缺失时（升级/清理后很常见），
  显式指定系统浏览器 `--browser-executable "C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe"`，
  或先跑 `npx remotion browser ensure` 重新下载。两条路都实测可用。
- **底图默认关闭**：`地图.显示底图=false` 时出片**不需要任何瓦片**，`public/` 空着就能渲。
  要开底图得自备瓦片放 `public/trail-tiles/`（不入库，见下方合规说明）。
- **本仓库只注册一个合成** `TrailProfile`：`remotion compositions` 只应输出一行；
  输出空列表就说明 bundle 出错（看报错，不要怀疑组件丢了）。
- **端口**：调参台默认 5232；Studio 的 3000 被占时用 `--port=3100`。
- **Studio 根路径会恢复「上次打开的合成」**：分享链接必须带合成名
  `http://localhost:3100/TrailProfile`，否则可能落到素材缺失的合成上、满屏红色报错。
- **调参台预览底板**跟随场景 `bgColor`：透明时铺 28px 棋盘格 —— 不铺就看不出透明是否生效。
- 调 Remotion CLI 用 `./node_modules/.bin/remotion`，不要用 `node node_modules/@remotion/cli/dist/index.js`
  （某些环境会静默失败：exit=0、无输出、无文件，最容易误判成功）。

## 12. 卫星截图叠加（SatelliteTrack）

> 本节只保留**做法与坑**，本仓库不含该合成的实现（`SatelliteTrack.tsx` / `sat-track-scene.mjs`
> / `check-sat-track.mjs` 都不在包内）。需要时按下面的规则自行实现，别从零试错。

用户给一张卫星截图 + 图上控制点经纬度，要求把轨迹叠上去 —— 另一套合成
（`src/SatelliteTrack.tsx` + `src/sat-track-scene.mjs` + `src/satellite-track-data.json`），
不复用 `trail-scene.mjs`（那边带剖面和相机适配，这边底图钉死）。

四条必读（细节见 [`references/satellite-overlay.md`](references/satellite-overlay.md)）：

0. **先问底图是正射还是 3D 倾斜**。Google Earth 那种带地形起伏的截图，山脊按 `d ≈ r·h/H` 沿径向位移（实测 20~50 px），**单应/相似只能描述平面→平面，加控制点也补不回来**（实测单应精修残差反而从 3.24 涨到 4.13 px）。正解是**换成高德卫星正射瓦片**跑解析标定：系统偏移 10 m → 0.9 m、残差 3.0 m → 1.8 m。判据：分象限拟合的尺度差 >3% 就是倾斜视图，别再拟合了。
1. **控制点量「针尖」不是图标中心**。推钉的针尖才是经纬度所指；量偏 9 px 会让标定把偏差当系统性位移消化，轨迹整体偏离图钉 11 px（≈10 m），1080p 上看不出来、对着图钉一看就露馅。
2. **平移自由度必须冻结**。放开平移（哪怕 ±14 px），优化器会为「平均亮脊更好看」把线推离控制点 15~17 px；单应要冻结 `H[2]/H[5]`。判据看**对齐残差**（σ / 中位偏移 / ≤3 px 占比），残差等价时按用户控制点走。
3. **改完标定先跑 `node scripts/check-sat-track.mjs`**（12 项断言），别靠肉眼。
4. **要手调就开调参台**：`npm run studio-sat` → `http://localhost:5234/sat-studio.html`，拖动画布即平移轨迹、Shift 转、Alt 缩、右键移视图、滚轮缩放视图，保存直接写回 JSON。
