# 卫星截图叠加（SatelliteTrack）

> 从 `SKILL.md` §12 拆出（2026-10-26）：那份主文档到 400 行上限，按 §11 的维护规矩拆成 reference。
> 触发场景：用户给一张卫星截图 + 图上一个控制点的经纬度，要求「把轨迹放到这张图上」。

## 卫星截图叠加（SatelliteTrack，2026-10-26 实做）

### 12.1 坐标链三段，缺一段整体偏
```
经纬度 → 归一化墨卡托（makeGeo）→ 截图像素（相似/单应，calib）→ 画面像素（cover 缩放 + framing.offsetPx）
```
标定参数全在 `calib` 里：`pinPx` / `anchorDistM` / `rotDeg` / `pxPerM` / `offsetPx` / `model` / `H`。
`pxPerM` 的初值永远取截图左下角**比例尺**（`scaleBar.px / scaleBar.meters`），不要取上一轮的 `pxPerM`——
否则每跑一次就放大约 4%，四轮后轨迹跑出画面（棘轮效应）。

### 12.2 硬规则：控制点量「针尖」，平移自由度冻结
- 用户标的黄色图钉是 Google Earth **推钉**，真值 = **针尖那根细暗线的最低点**，不是头部中心。
  取头部中心会偏 9 px；标定随后把这个偏差当成系统性位移去消化，整条轨迹被推离图钉 11 px（≈10 m）。
  量法：先按颜色分割取黄像素 bbox，再在下方看那根暗线的底端（`probe-pin.mjs` / `probe-needle.mjs`）。
- **不要让平移进搜索空间**。一旦放开（哪怕 ±14 px），优化器为了让平均亮脊更好看，
  会把线推离控制点 15~17 px。锚点是用户唯一给的硬证据，权重高于「平均好看」。
- 单应变换要冻结 `H[2]`/`H[5]`（= 原点处的平移 = 锚点），只动旋转/尺度/剪切/透视 6 项。
- 判据用**对齐残差**（沿线找亮脊峰的垂直偏移，中位/σ/≤3 px 占比），不要只用平均评分：
  实测两个解评分 11.4 vs 18.3，残差却几乎一样（σ 3.36 vs 3.32）。**残差等价时按控制点走。**

### 12.3 判据函数：亮脊评分，不是平均亮度
`score = I(p) − 0.5·(I(p+6n) + I(p−6n))`，n = 轨迹在该点的像素法向。
平均亮度会把线吸到整片亮坡；亮脊把它钉在窄路面上。**画幅是硬约束**：轨迹越出 40 px 安全区直接判负，
否则搜索会为了贴合把两端挤出画面。

### 12.4 截图预处理（`prep-sat-basemap.mjs`）
- 罗盘/比例尺/状态栏就地修补：**双镜面 50/50 混合 + 非镜面边 12 px 羽化**。
  单镜面会出「蝴蝶对称」，拉普拉斯扩散只扩 ~20 px 会留死黑方块，修完**不要再叠噪声**。
- 底部/角上的 HUD 可以先修再靠构图裁掉一部分（`fit-sat-framing.mjs` 会顺带切掉）。
- 图钉本身建议**保留**：它成了画面里一个「这里有标记」的锚点，硬抹四种修法都会留方块。
  **但要把自家起点标记换个颜色**（绿），否则和黄色图钉读成两个同款标记。

### 12.5 构图与文案
- `fit-sat-framing.mjs` 扫 `zoom / offsetPx`，约束「轨迹离四边 ≥56 px + 底图必须铺满（不露黑边）」，
  目标函数 = 轨迹占屏面积最大 + 居中偏差最小。`framing.offsetPx` 单位是**画面像素**，正 y = 底图下移。
- 实拍底图纹理比纯色背景「吵」得多：标题要 **40 / 19 px**（纯背景用 34 / 16 就够），读数 42 / 22，
  描边加粗到 6 / 5，否则副标题在影像上糊成一团。

### 12.6 出片与自检
```
npm run calib-sat     # 标定（--write 落盘；--free 只看自由解做对照）
npm run prep-sat      # 修底图 HUD
npm run still-sat     # 单帧
npm run render-sat    # out/sat-track.mp4（h264 / crf 18 / swangle）
node scripts/check-sat-track.mjs   # 12 项断言：锚点 0 px / 完整入画 / 生长单调 / 首尾里程 / 底图铺满 / 路径点数
```
**改任何标定参数后先跑 `check-sat-track.mjs`**：卫星版的错误全是「看着差不多」型，
锚点偏 11 px 在 1080p 上就是一粒米，肉眼扫不出来。

## 0. 底图选型：正射瓦片 vs 3D 倾斜截图（2026-10-26 重做）

**先去判断手上这张图是哪种，再决定要不要拟合。判断错了后面全是白费。**

### 0.1 怎么判
- 画面里**平行道路不平行、远处明显压缩** → 透视图。
- 分象限拟合（`scripts/diag-sat-perspective.mjs`）：近侧/远侧尺度差 **>3% 就是倾斜视图**（本例 1.1636 vs 1.2327 = 6%）。
- 更硬的判据：**单应精修后残差反而变大**（本例 σ 3.24 → 4.13 px）。单应能吃掉透视，但吃不掉「按高程位移」。

### 0.2 为什么平面变换补不回来
倾斜相机下，高差 h 的点在画面上沿径向被推开 `d ≈ r · h / H`（r 距像底点像素、H 相机高度）。
本例 r≈480 px、h≈150 m、H≈2 km → **d≈36 px（≈32 m）**。这不是"标定不准"，是信息本身不在一个平面上；
单应只能把平面映射到平面，加控制点只会拟合出「平均最优的平面」，山脊照样偏。

### 0.3 正解：换正射瓦片，标定变成算术
高德卫星瓦片 `https://webst0{1-4}.is.autonavi.com/appmaptile?style=6&x=&y=&z=`
（**要伪装 `Referer: https://www.amap.com/` 和 UA**）。优点：
- **GCJ-02**，与轨迹数据同系（本项目轨迹已纠偏），零转换；
- **正射**，地形位移恒为 0，谷底与山脊能同时贴合；
- **无 HUD**，不用再修补罗盘/比例尺（§4 那套双镜面可以扔了）；
- 不需要 key。**z=18 = 0.491 m/px；z=19 在山区返回「此区域无卫星图」占位图（≈4 KB 纯色）**。

三步：
```
node scripts/fetch-ortho-tiles.mjs          # 轨迹 bbox 取 1800 m 见方 → 256 张瓦片 → 4096×4096 PNG
node scripts/rotate-ortho.mjs --write      # 绕轨迹中心转 90°，长轴变横向才放得满 16:9
node scripts/fit-sat-framing.mjs --write
node scripts/check-sat-track.mjs
node scripts/score-ortho.mjs               # 客观体检：只评分不拟合
```
标定不再搜索：`pxPerM = 2^z·256 / mpu`（mpu = 该纬度 1 个归一化墨卡托单位的米数）、
`rotDeg` = 底图旋转角、`offsetPx = 0`、`pinPx` = 图钉经纬度换算的像素。**零拟合误差**。

旋转后 `pinPx` 的换算（`rotate-ortho.mjs` 已实现）：
`p' = c' + R(γ)·(p − c)`，展开即 `p' = [c' + R(γ)(pin − c)] + R(γ)·d·ppm` → 所以 `calib.rotDeg = γ`。

### 0.4 实测收益（同一段 2.9 km 轨迹）
| 指标 | Google 3D 截图 | 高德正射瓦片 |
|---|---|---|
| 最优平移 | 11.25 px ≈ 10 m | 1.8 px ≈ 0.9 m |
| 沿线亮脊残差 σ | 3.36 px ≈ 3.0 m | 3.71 px ≈ **1.8 m**（底图更密） |
| \|偏移\|≤3 px 占比 | 58.5% | 59.9% |

代价：高德影像偏暗、林区细节少（该区域影像较旧），观感不如 Google 有光影。

### 0.5 坑
- **Remotion 自带 ffmpeg 是精简版，没有 `tile` 滤镜**（`-h filter=tile` → Unknown filter）。拼图要
  `-i t_%03d.jpg p_%03d.png` 先批量转 PNG，再用 `png-decode` / `png-encode` 在 JS 里贴。**image2 输出从 1 开始编号**（p_001…），读的时候下标 +1。
- **坐标系必须用控制点验证，不能信数据里的 meta 字段**：轨迹可能被"无条件纠偏"过。
  拿用户给的图钉经纬度同时算「原值」与「纠偏后」到轨迹的距离，差几百米一眼可判（`scripts/verify-crs-pin.mjs`）。
  本例：图钉原值距轨迹 1.99 m → 说明图钉**也是 GCJ-02**（在奥维/高德里取的），当 WGS 再转一次就偏 219 m。
